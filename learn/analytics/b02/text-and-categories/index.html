Text cleaning and consistent categories

“North”, “north ”, “N.” and “Nrth” are one region to a person and four to a computer. Learn to normalise whitespace, case and Unicode, consolidate variants with a reviewed mapping table, split and extract fields with simple patterns, and see how consolidation changes counts and averages.

About 70 minutes

Before you start

You will be able to

  • Identify the whitespace, case, punctuation and Unicode differences that make equal-looking text values unequal.
  • Normalise text values by trimming, case normalisation and Unicode normalisation, in a sensible order.
  • Build and maintain a mapping table that consolidates variants into a controlled vocabulary.
  • Use simple regular expressions to check, extract and split text, and explain their limits.
  • Calculate how category consolidation changes group counts and averages.

Review first

  • Incorrect data types and inconsistent dates — You need data types, locales and the habit of converting with an explicit rule and then validating.
  • Duplicate records — Near duplicates and edit distance reappear here, applied to category values.

The idea

Fictional case

Lantern’s marketing team wants to split next quarter’s promotion budget across Lantern’s five delivery regions, North, South, East, West and Central, in proportion to orders. Lantern’s analyst, Jun Park, counts orders by region in the online-shop export and gets more than five groups. Customers type their region in the app, staff key some orders by hand, and the export has kept every version: capitals and lower case, stray spaces, abbreviations such as “N.” and typing errors such as “Nrth”. The product names have the same problem.

People read “North”, “north ” and “N.” as the same region. Software compares text exactly, character by character, so it sees three different values. Every operation that relies on equal values is affected: counting and grouping split one category into several, filters miss rows, and joins to another table fail. This lesson turns the many ways of writing a value into one agreed value, and keeps a record of how.

Whitespace you can’t see

Whitespace is any character that shows as blank space: the ordinary space, the tab, line breaks and several special spaces. It causes trouble in three places. Leading and trailing spaces (“North␣”) are invisible on screen but make the value unequal to “North”. Doubled spaces inside a value (“House␣␣Blend”) make two product names differ. And special spaces look identical to an ordinary space but are different characters.

The most common special space is the non-breaking space (Unicode U+00A0), which word processors and web pages use to keep two words on the same line. It arrives when text is copied from a web page or a document, and several locales use spaces like it as thousands separators. Because it isn’t the ordinary space, some cleaning functions leave it alone. Microsoft’s documentation says Excel’s TRIM removes only the ordinary 7-bit ASCII space (character 32) and does not, by itself, remove the non-breaking space (character 160). In this lesson’s tables, ␣ marks an ordinary space and ⍽ a non-breaking one, so that you can see them.

A quick way to find invisible characters is to compare lengths: “North” has 5 characters, and if a value that looks like “North” has 6, something is hidden in it.

Case and punctuation

Case normalisation converts text to a single case, so that “NORTH”, “north” and “North” compare equal. For matching, convert everything to lower case (or, in Python, use casefold(), which goes further: its documentation notes that the German “ß” becomes “ss”, which lower() leaves unchanged). For display, keep a properly capitalised version: the controlled value “North” rather than “north”. Punctuation needs a decision of its own: “N.” and “N” are the same abbreviation, but removing every full stop would also change values in which a full stop matters, such as decimal numbers inside product descriptions.

Characters that look the same but aren’t

Computers store text as a sequence of code points: the numbers that the Unicode standard assigns to characters, written like U+0065 for “e”. Some characters can be stored in more than one way. The letter “é” can be one code point, U+00E9, or two: “e” followed by a combining acute accent, U+0301. Both display as “é”, but a program comparing code points sees “Café” (4 code points) and “Café” (5 code points) as different strings. Which form you get depends on the keyboard, the operating system and the software that produced the text.

Unicode defines rules that put equivalent text into one standard form. Unicode normalisation converts text to one of the forms set out in Unicode Standard Annex #15. NFC composes characters wherever possible, so “e” plus the combining accent becomes the single code point U+00E9; NFD decomposes them. Normalising every value to NFC before comparing makes the two “Café”s equal.

Variants, typos and one agreed list

After whitespace, case and Unicode are dealt with, what remains are genuine variants: abbreviations (“N.”), typing errors (“Nrth”, “Wset”) and alternative names (“Centre” for “Central”). These need a person’s judgement once, and then a rule that applies it every time. The rule lives in a mapping table: a two-column table (with notes) that lists each variant and the value it should become. The values it maps to come from a controlled vocabulary: the agreed list of allowed values for the column, usually set in the data dictionary. For Lantern’s regions the vocabulary is the five names North, South, East, West and Central.

Mapping many variants onto the values of a controlled vocabulary is category consolidation. It looks like tidying labels, but it changes numbers: every count, share and average by category is calculated from different rows after consolidation, and rankings can reverse. The worked examples measure how much.

Key idea: Normalise, map, validate, and keep the raw value

Fix mechanical differences first (Unicode form, whitespace, case), then map the remaining variants with a reviewed mapping table, then check that every value is in the controlled vocabulary and flag the ones that aren’t. Write the result to a new column and keep the original beside it.

In depth

An order of operations

The order matters, because each step makes the next one simpler and safer.

  1. Keep the raw value. Write cleaned values to a new column, so every change can be traced and undone.
  2. Normalise Unicode (NFC). Do it first, so later steps compare like with like.
  3. Fix whitespace. Replace non-breaking and other special spaces with ordinary ones, remove leading and trailing spaces, and collapse runs of spaces inside the value to one.
  4. Normalise case for the matching key, usually lower case.
  5. Standardise punctuation where it carries no meaning, for example removing the full stop in “N.”.
  6. Map variants to the controlled vocabulary with the mapping table.
  7. Validate. Every cleaned value should be in the vocabulary. Count and list the ones that aren’t, and flag them rather than forcing them into a category.

Doing it in this order keeps the mapping table short. Map before trimming and lower-casing, and the table needs separate rows for “North”, “north”, “North␣”, “NORTH” and every other combination; miss one and it slips through. After steps 2 to 5, all of those are already “north”, and the table needs only the genuine variants.

The tools differ in what “trim” means, so check yours. Excel’s TRIM removes leading and trailing ordinary spaces and also collapses doubled spaces between words to one, but not non-breaking spaces; the usual fix is to replace character 160 with an ordinary space first, as in =TRIM(SUBSTITUTE(A2, CHAR(160), " ")). PostgreSQL’s trim removes only the space character by default. Python’s str.strip() and pandas’s str.strip() remove whitespace of any kind, including non-breaking spaces and newlines, from both ends, but leave doubled spaces inside the value.

Unicode normalisation in a little more depth

Unicode Standard Annex #15 defines four normalisation forms. Two rest on canonical equivalence, which the annex describes as a fundamental equivalence between characters or sequences of characters: sequences that represent the same abstract character and should look and behave the same. NFD (canonical decomposition) splits characters into base letters and combining marks; NFC (canonical decomposition followed by canonical composition) puts them back together wherever a single code point exists. NFC is the usual choice for storing and comparing text, and it is the default of PostgreSQL’s normalize function.

The other two forms, NFKD and NFKC, also apply compatibility mappings, which fold characters that differ only in presentation: the ligature “ﬁ” becomes the two letters “fi”, full-width letters such as “Ａ” become ordinary ones, and a non-breaking space becomes an ordinary space. That is useful for building a matching key and risky for stored text, because it throws information away. Neither kind of normalisation removes accents: “Café” and “Cafe” stay different. Stripping accents is a separate, deliberate decision, and a lossy one, since it can merge different words and misspell names.

Mapping tables and controlled vocabularies

Keep the mapping as data, not as a string of find-and-replace operations or a formula buried in one cell. A small table with one row per variant can be read, reviewed and changed by people who don’t write code.

Three habits make a mapping table trustworthy. Review: someone who knows the business approves each new row, because only they can say whether “Northern” is a spelling of North or a different delivery zone. Version: the table changes as new variants appear in each month’s export, so date or number each version and record which version cleaned which file. Flag, don’t force: a value with no row in the table is reported, not pushed into the nearest category or an “Other” bucket, where it would quietly distort the counts.

Fuzzy matching helps build the table but shouldn’t replace it. An edit distance of 1 between “Nrth” and “North” is a good reason to suggest a mapping; a person then confirms it. Some vocabularies are set by outside standards rather than by the business. ISO 3166, for example, defines internationally recognised codes for countries, so “GB” is the two-letter ISO code for the United Kingdom. Harborview Hotel’s data dictionary instead uses full English country names, so its analysts map codes such as GB and US, abbreviations such as USA and alternative names to the names in that list.

Splitting and combining fields

A column sometimes holds several variables at once. Wickham (2014) lists “multiple variables are stored in one column” among the five most common problems with messy datasets, and tidy data gives each variable its own column. Lantern’s product names include the pack size (“Decaf Colombia 1kg”), and its export also has a separate size_g column. Extracting the size from the name and comparing it with size_g is a cross-field check that catches rows where the two disagree.

People’s names are the classic trap. Splitting “Ana Lim” at the space gives a given name and a family name, but the same rule fails for many real names: in many East Asian naming conventions the family name comes first (Lim Wei Ling’s family name is Lim), family names can contain spaces (“de la Cruz”), and some people use a single name. Split names only when an analysis needs the parts, keep the full name as it was given, and never treat the split as more reliable than the original. Combining goes the other way, and is usually safer: a matching key such as the trimmed, lower-cased email address, or a single timestamp built from separate date and time columns.

Regular expressions

A regular expression (regex) is a pattern that describes a set of strings. Spreadsheets, SQL databases and pandas all support them for finding, checking, extracting and replacing text. A handful of pieces covers most cleaning work.

Three patterns show what they are good for. Replacing \s+ with a single space collapses every run of whitespace. The pattern ^\d{5}$ is a format check: it accepts “02134” and rejects “2134”, “02134-1234” and “␣02134”. And (\d+)\s?(g|kg) extracts a pack size from a product name, returning “250” and “g” from “House Blend 250g” and “1” and “kg” from “Decaf Colombia 1kg”. A first attempt such as (\d+)\s?g would have missed the kilogram packs entirely, and “250G” in capitals would defeat both unless the match ignores case. Test every pattern on the real values, including the odd ones, before trusting it.

Patterns describe the shape of text, not its meaning. Email addresses show the limit. A pattern such as ^[^@\s]+@[^@\s]+\.[^@\s]+$ (something, an @, something, a dot, something) catches obvious errors such as a missing @ or a space, but it accepts “maya@example..com”, which no mail server would deliver to, and rejects some addresses that the formal email syntax allows. The HTML Standard, which defines how browsers check email fields, deliberately departs from that formal syntax (RFC 5322), calling it too strict before the @, too vague after it and too lax in other ways to be practical. A pattern can tell you that a value looks like an email address; only a message that arrives proves it is one.

How consolidation changes the numbers

When variants are merged, each consolidated category’s count is the sum of its variants’ counts, and its mean is the weighted average of the variants’ means (formula below). Before consolidation, an analysis that filters on the exact value “North” sees only the rows spelled that way. If the variants were a random sample of North’s orders, North’s average would merely be estimated from fewer rows. They rarely are: variants come from particular sources (staff keying phone orders, one version of the app, one marketplace), and those sources differ in what customers order. The correctly spelled rows are then a biased subset, and both counts and averages, and the rankings built on them, can change after consolidation.

Keeping the raw values

Never overwrite the original text. Keep region_raw and region side by side, keep the mapping table and its versions, and keep the code or recipe that applies them. Then anyone can see what each value was, why it changed and which version of the rules changed it, and a mistake in the mapping can be corrected by fixing one row and rerunning, rather than by hunting for edits made by hand. In pandas the whole recipe can be one readable chain: s.str.normalize('NFC').str.replace(r'\s+', ' ', regex=True).str.strip().str.casefold().map(mapping), where the replacement turns every run of whitespace, non-breaking spaces included, into one ordinary space, and map turns any value missing from the mapping into a missing value that you can count and flag.

Common mistakes

  • “Trimming removes every kind of space.”

    It depends on the tool. Excel’s TRIM ignores the non-breaking space, and PostgreSQL’s trim removes only ordinary spaces by default, while Python’s strip() removes both but leaves doubled spaces inside the value. After trimming, check the lengths of values that should be equal.

  • “Find and replace is a quick way to fix variants.”

    Replacing text inside values changes more than you intend: replacing “N.” with “North” also turns “N.E. depot” into “NorthE. depot”, and replacing “Cent” with “Central” turns every correct “Central” into “Centralral”. Map whole values through a mapping table, after normalising them, so each rule applies only to the value it names.

  • “Every value should end up in a category.”

    Forcing an unknown value into the nearest category or an “Other” bucket hides it. Flag unmapped values, count them, and add a mapping row only after someone has confirmed what the value means.

  • “If two values look identical, they are identical.”

    A trailing space, a non-breaking space or a different Unicode form for “é” is invisible on screen. Compare lengths, normalise to NFC and replace special spaces before concluding that a join or a filter has failed for some other reason.

  • “A regular expression can check that an email address is real.”

    A pattern checks shape only. Simple patterns accept addresses no server will deliver to and reject some the formal syntax allows. Use a pattern to catch obvious typing errors, and a confirmation message to prove an address works.

  • “Consolidating categories only tidies the labels.”

    It changes which rows each category contains, so counts, shares, averages and rankings can all move, as the North and South example showed. Compare the key results before and after consolidation and report the difference.

In practice

Regional marketing at Lantern. The promotion budget is allocated by region, so the region column is a financial input. Jun Park, Lantern’s analyst, cleans it with a fixed recipe (NFC, whitespace, lower case, mapping table, validation), reports the vocabulary coverage of every monthly export, and sends new unmapped values to the operations team, who know which towns belong to which delivery region. When coverage dropped one month, the cause was a new app version that offered “Centre” instead of “Central”: one reviewed row in the mapping table fixed it for every future export.

Programme reports at Northfield University. Northfield’s student records spell programme names in several ways: abbreviations such as “Bus. Admin.”, an acronym such as “CS”, capitals, trailing spaces and the occasional typing error. The registry’s official programme list is the controlled vocabulary. Before planning analysts compare grade point averages across programmes, they map every variant to the official name and check that the number of students per programme matches the registry’s own headcount. A programme whose students are split across four spellings would otherwise appear smaller than it is, and its average would be computed from a biased subset.

Product data. Stray spaces and inconsistent capitals in product names split one product’s sales across several rows of every report, and make stock counts disagree with sales. Retailers therefore keep a product master list, with one row per product and its official name, and match every order line to it by a cleaned key rather than by the name as typed. Regular expressions earn their place here as checks: extracting the pack size from each product name and comparing it with the recorded size flags rows where one of them is wrong.

Guest origins at Harborview. The hotel’s country column feeds advertising budgets and reports to the regional tourism office. Because different booking channels write countries differently, the hotel maps every incoming value to its controlled list as bookings arrive, keeps the raw value, and reviews the mapping table each quarter. The applied example showed what skipping this step costs: a budget split that put the hotel’s second-largest market third.

Summary

  • Software compares text character by character, so case, whitespace, punctuation and Unicode form make equal-looking values unequal and split categories.
  • Clean in order: keep the raw value, normalise Unicode (NFC), fix whitespace including non-breaking spaces, normalise case, standardise punctuation, map, validate.
  • Tools differ: Excel’s TRIM ignores the non-breaking space, and PostgreSQL’s trim removes only ordinary spaces by default.
  • Keep the mapping in a reviewed, versioned mapping table that maps variants to a controlled vocabulary; flag unmapped values instead of forcing them.
  • Regular expressions check, extract and replace text by its shape; test them on real values and remember that shape is not meaning.
  • Consolidation adds variant counts and takes a weighted mean of variant means; it can reverse rankings, so compare key results before and after.

Terms introduced

Whitespace
Characters that display as blank space, including the ordinary space, tabs, line breaks and special spaces such as the non-breaking space.
Non-breaking space
A space character (Unicode U+00A0) that looks like an ordinary space but is a different character, often left behind by web pages and documents, and not removed by some trim functions.
Code point
The number the Unicode standard assigns to a character, written in the form U+00E9.
Case normalisation
Converting text to a single case, usually lower case, so that values differing only in capitals compare as equal.
Unicode normalisation
Converting text to one of the standard forms defined in Unicode Standard Annex #15 (NFC, NFD, NFKC, NFKD), so that equivalent characters are stored the same way.
Mapping table
A table that lists each variant of a value and the value it should become, kept as reviewed and versioned data rather than as one-off edits.
Controlled vocabulary
The agreed list of allowed values for a column, usually set in the data dictionary or by an outside standard.
Category consolidation
Merging the variants of a categorical value into the values of a controlled vocabulary, which changes the counts and statistics of each category.
Regular expression
A pattern that describes a set of text strings, used to find, check, extract or replace text.
