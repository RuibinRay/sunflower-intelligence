Incorrect data types and inconsistent dates

A price stored as text won’t add up, and a date stored as text won’t sort. Learn to give every column the right data type, convert numbers written in different local formats, keep identifiers as text, and turn a column of mixed dates into unambiguous ISO 8601 dates without guessing.

About 75 minutes

Before you start

You will be able to

  • Identify the data type each column should have, and explain how a wrong type breaks sorting, sums and joins.
  • Convert numbers stored as text, including currency symbols, thousands separators, decimal commas and negatives in parentheses.
  • Recognise identifiers that look numeric but must stay text, such as codes with leading zeros.
  • Convert dates in mixed formats to ISO 8601, resolving ambiguous dates with evidence rather than guesswork.
  • Calculate the date behind a spreadsheet serial number, and the serial number of a date, in the 1900 date system.
  • Explain how to store and report times so that time zones and daylight saving don’t corrupt them.

Review first

  • Profiling a dataset and writing validation rules — You need format checks, range checks and cross-field checks, and the habit of profiling a column before converting it.
  • Duplicate records — Duplicate detection depends on values being stored consistently; this lesson makes them so.
  • Reading dates written in different ways, and adding or subtracting days.

The idea

Fictional case

Lantern’s bookkeeper totals the unit_price column of the March order export and gets a number far too small, with no error message. She sorts by order_date and finds orders from June sitting between two orders from March. The export, lantern-orders, has collected values from the web shop, the app and older spreadsheets, and each wrote prices and dates its own way: prices with and without a dollar sign, one with a decimal comma; dates such as 2026-03-04, 04/03/2026, 3/14/26, March 5, 2026 and 46085. Nothing is missing. The values are just not stored as what they mean.

Every column in a dataset has a data type: the kind of value it holds, which determines what software can do with it. Numbers can be added, averaged and compared by size. Dates can be put in time order, subtracted to give a number of days, and grouped by week or month. Text can be compared, searched and sorted alphabetically. A boolean holds one of two values, true or false.

The four basic data types

Most data arrives as text, because a CSV file is text. A program reading it has to decide what each column is, and when the values are messy it often gives up and leaves the whole column as text. The column still looks fine on screen. It fails only when you use it.

How a wrong type fails, usually without an error message

Microsoft’s own documentation spells out the spreadsheet case: SUM ignores text values and adds only the numeric ones, while a formula such as =A1+B1 returns a #VALUE! error when a cell contains text. The silent version is the dangerous one.

Conversion, deliberate and automatic

Type conversion turns a value of one type into another: the text “14.50” into the number 14.5, or the text “04/03/2026” into the date 4 March 2026. It can be deliberate, when you state how each value should be read, or automatic, when software guesses. Spreadsheets guess as soon as you type or open a file. Microsoft lists the conversions Excel makes by default: it removes leading zeros from numerical text (00123 becomes 123), keeps only 15 digits of precision for long numbers, turns digits around the letter E into scientific notation (123E5) and turns some letter-and-number strings such as JAN1 into dates. Recent versions (Excel for Microsoft 365 and Excel 2024) let you switch these conversions off.

Automatic conversion has damaged real research. Ziemann, Eren and El-Osta (2016) scanned supplementary spreadsheets published in leading genomics journals and found that roughly one paper in five with Excel gene lists contained gene names that had been converted to dates or floating-point numbers. The software did exactly what it was designed to do; nobody had told it what the column meant.

Key idea: Convert deliberately, then count the failures

For every column, decide the type it should have, state the format the source used, convert with that format, and count the values that failed to convert. A conversion that fails loudly is a gift: it shows you exactly which values need a decision.

In depth

Numbers stored as text

Numbers end up as text because of what is written around or inside them. Each pattern needs its own rule.

Common ways a number is written as text

The decimal mark and the thousands separator depend on the writer’s locale: the conventions for a language and region, covering decimal and grouping marks, date order, currency and more. Software stores these conventions as locale data. Formatted for the United States or the United Kingdom, one thousand two hundred and fifty is 1,250.00; for Germany, 1.250,00; for France, 1 250,00, where the gap is a narrow non-breaking space. The same characters mean different numbers in different locales: “1,250” is one thousand two hundred and fifty to an American reader and one and a quarter to a German one. Nothing in the value tells you which; only its source does.

So convert numbers source by source. Find out which locale each source used, then for each value: remove the currency symbol (recording the currency in its own column if there is more than one), remove the grouping separator, replace the decimal mark with a point, turn parentheses and Unicode minus signs into an ordinary minus, and parse. Parsers are strict about that last detail. Python’s float(), for example, rejects “−45” written with the Unicode minus. Decide once whether a percentage column holds fractions (0.12) or percentage points (12) and say so in the data dictionary.

Then validate. Count the values that failed to convert and look at every one of them. Range-check the ones that succeeded: a coffee price of $1,800.00 converts perfectly and is almost certainly a typing error for $18.00. Conversion makes values comparable; it doesn’t make them right.

Identifiers that look like numbers

Postcodes, account numbers, phone numbers, product codes and student numbers are made of digits, but they are labels, not amounts. Nobody adds two postcodes or averages two phone numbers. Store them as text. Stored as numbers they lose information: a code such as 004517 loses its leading zeros and becomes 4517, and a 16-digit card or account number loses its last digit, because Excel keeps at most 15 significant digits and turns the rest into zeros. A useful test is to ask whether arithmetic on the column would ever make sense; if not, it is text, however numeric it looks.

Lost leading zeros can be restored only when you know the code’s exact width. If the data dictionary says every site number has six digits, padding 4517 with zeros to 004517 is safe. If codes come in several lengths, padding invents codes; go back to the source and import the column as text. Digits lost beyond the 15th cannot be recovered at all.

Dates in different orders

People write the parts of a date in different orders: day/month/year in most of the world, month/day/year as the usual order in the United States, and year-month-day in ISO 8601 and in several East Asian conventions. A value such as 25/03/2026 can be read only one way, because there is no month 25. A value such as 04/03/2026 can be read as 4 March or as 3 April. An ambiguous date is one whose day and month could be swapped to give a different valid date.

Ambiguity is common. A date is ambiguous when its day number is 12 or less and differs from its month number. In a year of 365 days, 144 dates have a day number of 12 or less; 12 of them (1 January, 2 February and so on to 12 December) read the same either way, which leaves 144−12=132144 - 12 = 132144−12=132 genuinely ambiguous dates, about 132÷365≈36%132 \div 365 \approx 36\%132÷365≈36% of the year. More than a third of slash-dates can’t be read without outside information.

Resolve them with evidence, in this order:

  1. The source’s convention. Documentation, export settings or the system’s locale often state the format outright.
  2. Other values from the same source. If a source writes 14/03/2026 anywhere, it puts the day first. This works only if the source is one system or one person using one convention throughout; check that no value from the source contradicts it.
  3. Business rules. An order can’t be placed after it was dispatched, a check-in can’t follow its check-out, and every date should fall within the export period. These cross-field checks and range checks often rule out one reading.
  4. Ask, or flag. If both readings survive, ask the person or team who produced the value. If nobody can say, flag the value as unresolved and record the decision. Never guess silently.

Caution: Settings that prefer a reading are not rules

Many tools have an option that sounds like a fix. pandas’s documentation warns that dayfirst=True “is not strict”: it prefers day-first but will still read a value such as 03/15/2026 month-first rather than fail. When values are parsed one at a time (with format='mixed', or by default before pandas 2.0) a mixed column can therefore come out partly day-first and partly month-first with no error. Since pandas 2.0 the default instead infers one format from the first value and stops with an error at the first value that doesn’t fit it, which is safer but still a guess. Pass an explicit format for each source, so that a value that doesn’t fit fails loudly and you chose the format.

Two-digit years need a century rule too. Python’s %y, for example, reads 00–68 as 2000–2068 and 69–99 as 1969–1999. Written-out dates bring their own problems: month names depend on language (“4 mars 2026” is French), and some, such as “Mar 4”, have no year at all.

ISO 8601

The international standard for writing dates and times is ISO 8601. Its usual date format is YYYY-MM-DD, as in 2026-03-04 (the standard calls this the extended format; its basic format drops the hyphens, 20260304), with the units running from largest to smallest: year, month, day, then hour, minute, second. That order makes the format unambiguous and means that dates written this way sort correctly even as text. The current edition is published in two parts, ISO 8601-1:2019 (basic rules) and ISO 8601-2:2019 (extensions). A date and time is written with a T between them, and a time can carry its relation to UTC: 2026-03-14T23:30:00Z means 23:30 in UTC (the Z stands for an offset of zero), and 2026-03-14T18:30:00-05:00 is the same instant written as a local time five hours behind UTC. RFC 3339, the profile of ISO 8601 used in internet protocols, defines the offset as local time minus UTC.

Spreadsheet serial dates

Spreadsheets store a date as a serial date: a count of days from a starting point, displayed through a date format. Change the cell’s format to General and 4 March 2026 appears as 46085. That is why serial numbers turn up in exports: somewhere, a date cell lost its format or was saved as a number.

Excel has two systems. In the 1900 date system, the default in Excel for Windows and in current Excel for Mac, 1 January 1900 is serial number 1. When Lotus 1-2-3 was first released it treated 1900 as a leap year, which it was not, and Excel kept the same assumption so that its serial numbers matched Lotus’s. Excel therefore counts a 29 February 1900 that never happened (serial 60). Microsoft judged that correcting it would shift almost every existing date by a day and break compatibility, and the only visible symptom it lists is that the WEEKDAY function is wrong for dates before 1 March 1900. For any date from 1 March 1900 onwards, the serial number is simply the number of days since 30 December 1899:

S1900=date−30 December 1899(in days)S_{1900} = \text{date} - \text{30 December 1899} \quad (\text{in days})S1900​=date−30 December 1899(in days)

The 1904 date system, the default in earlier versions of Excel for Mac, counts from 1 January 1904 as day 0. The two systems differ by 1,462 days, four years and one leap day: Microsoft’s own example gives 5 July 2011 as 40729 in the 1900 system and 39267 in the 1904 system. If a workbook used the 1904 system and its serial numbers are read as 1900-system numbers, every date comes out four years and a day early.

You can recognise serial numbers by their size: in the 1900 system, 1 January 2025 is 45658 and 31 December 2026 is 46387, so five-digit integers between those values in a date column are almost certainly dates in 2025 or 2026. Convert them with the origin stated, for example pd.to_datetime(s, unit='D', origin='1899-12-30') in pandas, and check a few results against the source.

Times and time zones

A timestamp without a time zone is ambiguous in a different way. Lantern’s shop records order times in UTC. Suppose Lantern’s local time is five hours behind UTC. An order placed at 23:30 local time on 14 March is stamped 2026-03-15T04:30:00Z, so a report that groups orders by the UTC date moves it into 15 March. Neither date is wrong; they answer different questions. Store timestamps in UTC, or as local time with its offset, and choose the time zone of every daily, weekly or monthly report deliberately, usually the business’s own local day.

Never store local clock times without an offset. Where clocks change for daylight saving, an hour of local time is skipped each spring and an hour is repeated each autumn, so a local time in the repeated hour could be either of two instants, and durations that span a change come out an hour wrong. An offset, or a stored time in UTC, removes both problems.

Booleans written many ways

A yes/no column, such as Lantern’s subscription, can arrive as Y/N, yes/no, TRUE/FALSE, 1/0, “subscribed” or a tick. Convert it with an explicit list of accepted spellings for true and for false, and flag anything else. Treat a blank as missing, not as false: a blank means nobody recorded the answer, which is a different fact from “no”, and a later lesson in this course deals with missing values properly.

Convert with an explicit format, then validate

  1. Profile the raw column: list the distinct patterns (for example, the share of values that look like 99/99/9999, 9/9/99 or five-digit integers) and which source each comes from.
  2. Decide the target type and, for each source, the exact format it used.
  3. Convert each pattern with its explicit format, keeping the raw column untouched beside the converted one.
  4. Count the values that failed and look at each one; fix the rule or flag the value.
  5. Validate the result with range checks and cross-field checks, and record any value you resolved by judgement.

The tools differ only in syntax. In a spreadsheet, import identifier columns as Text (Microsoft recommends doing this on import, for example with Power Query) and rebuild dates from their parts with DATE, so that the order of day and month is your decision. In SQL, PostgreSQL’s to_date(order_date, 'DD/MM/YYYY') and to_number take an explicit format. In pandas, pd.to_datetime(s, format='%d/%m/%Y', errors='coerce') and pd.to_numeric(s, errors='coerce') turn values that don’t fit into missing values you can count, rather than stopping at the first one.

Common mistakes

  • “If it looks like a number, store it as a number.”

    Identifiers such as postcodes, account numbers and site numbers are labels. Stored as numbers they lose leading zeros, long ones lose digits beyond the 15th, and joins fail. Ask whether arithmetic on the column would ever make sense; if not, keep it as text.

  • “The software will work out the date format.”

    Automatic parsing guesses value by value. Settings such as pandas’s dayfirst=True express a preference, not a rule, so a mixed column parsed value by value can be read partly day-first and partly month-first without an error. State the format for each source and let mismatches fail.

  • “A comma always separates thousands.”

    In many locales the comma is the decimal mark: 19,50 is nineteen dollars fifty, and 1.250,00 is one thousand two hundred and fifty. The value alone can’t tell you which convention it follows; find out the locale of each source before converting.

  • “Serial number 1 is 1 January 1900, so add the serial number to that date.”

    That lands two days late for any modern date: adding 46082 days to 1 January 1900 gives 3 March 2026, while serial 46082 is 1 March 2026. One day comes from day 1 being 1 January rather than day 0, and the other from Excel’s non-existent 29 February 1900. Count from 30 December 1899 instead.

  • “Local time is fine; the business is only in one place.”

    Customers and systems aren’t. Servers often record UTC, and daylight saving repeats an hour of local time every autumn. Store UTC or local time with its offset, and choose the reporting day deliberately.

  • “A blank in a yes/no column means no.”

    A blank means the answer wasn’t recorded. Converting it to false invents information and biases any rate calculated from the column. Map the accepted spellings of yes and no explicitly and treat everything else, blanks included, as missing or flagged.

In practice

Daily sales at Lantern. Ana asks whether Sunday is the shop’s strongest day. Her shop platform stores order times in UTC, so evening orders in Lantern’s own time zone fall into the next UTC day, and a chart by UTC date would shift a slice of every Sunday into Monday. The analyst converts every timestamp to Lantern’s local time before grouping by day of the week, notes in the report that “day” means Lantern’s local day, and checks the result against the till’s own daily totals.

Buying from abroad. Lantern buys green coffee from a supplier whose invoices are written in a European format, with dots between thousands and commas before the cents. When the bookkeeper pastes a statement into a US-formatted spreadsheet, some amounts become text and others are read as the wrong number. She now imports the supplier’s files with the locale stated, checks that the converted total equals the total printed on the statement, and only then records the invoices.

Hotel stays. Harborview Hotel receives bookings from its own website, from travel agencies and by phone, and the dates arrive in different formats. Nights are calculated as check-out minus check-in, which only works once both columns are true dates. The hotel’s analysts convert each channel’s dates with that channel’s format, recompute the nights, and use a cross-field check (nights must equal the difference between the dates) to catch the bookings where something is still wrong.

Warranty claims. At Kestrel Battery Installers the type of one column decided whether five customers were paid. The data team added two rules to its process: identifier columns are imported as text, and every join reports how many rows found no match. A match rate that suddenly drops, as it did from 100% to 37.5% in the applied example, is treated as a data problem to investigate before it is treated as a business finding.

Summary

  • A data type (number, text, date and time, boolean) determines what software can do with a column; a wrong type breaks sorting, sums and joins, usually without an error.
  • Convert numbers stored as text source by source: know the locale, remove currency symbols and grouping separators, handle decimal commas, parentheses and Unicode minus signs, then count the failures and range-check the results.
  • Identifiers made of digits are text. Leading zeros can be restored only when the code’s width is fixed and documented.
  • About a third of slash-dates are ambiguous. Resolve them from the source’s convention, unambiguous values from the same source and cross-field checks; flag what remains rather than guessing.
  • Write dates in ISO 8601 (YYYY-MM-DD); store times in UTC or with their offset, and choose the reporting time zone deliberately.
  • Excel’s 1900 date system stores days since 30 December 1899 for dates from 1 March 1900, because it counts a fictitious 29 February 1900; the 1904 system is 1,462 days behind.
  • Convert with an explicit format, keep the raw column, and validate the result.

Terms introduced

Data type
The kind of value a column holds (such as number, text, date and time, or boolean), which determines the operations that make sense on it.
Type conversion
Turning a value of one data type into another, for example the text “14.50” into the number 14.5. Deliberate when the format is stated, automatic when software guesses.
Locale
The conventions of a language and region for writing numbers, dates, times and currency, such as the decimal mark, the thousands separator and the order of day and month.
Leading zero
A zero at the start of a code, such as the first two digits of 004517. It carries no numerical value but is part of the identifier, and is lost if the code is stored as a number.
Ambiguous date
A date written so that its day and month could be swapped to give a different valid date, such as 04/03/2026 (4 March or 3 April).
ISO 8601
The international standard for representing dates and times, with units from largest to smallest; dates are usually written YYYY-MM-DD (its extended format) or YYYYMMDD (its basic format).
Serial date
A date stored as a count of days from a fixed starting point, as spreadsheets do. In Excel’s 1900 date system, 1 January 1900 is serial number 1.
UTC
Coordinated Universal Time, the reference time scale against which time zones are defined by their offsets, such as −05:00.
