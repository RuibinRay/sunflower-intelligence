Duplicate records

A record counted twice inflates revenue, customer numbers and averages without any warning. Learn to tell exact copies, conflicting versions and near duplicates apart, decide what counts as “the same” for the business, and remove duplicates without deleting genuine repeat orders.

About 80 minutes

Before you start

You will be able to

  • Distinguish exact duplicates, repeated keys with conflicting values and near duplicates, and explain how each kind arises.
  • Identify the business key that defines “the same record” for a dataset, and the evidence that separates a duplicate from a genuine repeat.
  • Choose a survivorship rule (first, latest update, most complete or merge) for a group of duplicates and justify it.
  • Calculate how duplicates distort totals, counts and averages.
  • Compute the edit distance between two short strings and explain how fuzzy matching uses it.
  • Find duplicates with a spreadsheet, with SQL and with pandas.

Review first

  • Datasets: rows, columns, records and variables — You need the unit of observation and the idea of a primary or composite key.
  • Profiling a dataset and writing validation rules — You need uniqueness as a data quality dimension and the habit of profiling a column before changing it.
  • Sums, counts and averages.

The idea

Fictional case

Ana Lim’s Lantern Coffee Co. now sells beans and coffee subscriptions through an online shop. At the end of each month the shop platform produces an order export, lantern-orders, with one row per order and columns such as order_id, order_date, customer_id, email, product, quantity, unit_price and order_total. When Lantern’s bookkeeper adds up order_total for March, the result is higher than the money the payment provider actually paid out. Nobody has stolen anything. Some orders are in the file more than once.

A duplicate record is a row that describes the same real-world thing as another row in the same dataset: the same order, the same customer, the same hotel booking. Almost every analysis assumes that each thing is recorded once. If the unit of observation is one order, each order should occupy exactly one row; a second row for the same order makes the data say that something happened twice when it happened once.

Duplicates are dangerous because nothing about them looks wrong. A copied row has a valid date, a sensible price and a real customer, so it passes every range check and format check. It only shows up when you ask a question about the table as a whole: are the keys unique, does the total agree with another source, why does this customer have two accounts?

Records like A, B and C, which describe the same entity but whose values differ slightly, in case, spacing, spelling or abbreviation or because the person used two addresses, are near duplicates. Exact comparison misses them; finding them takes standardisation and a measure of similarity, both introduced below.

Where duplicates come from

  • Exports and loads. A report is run twice and both files are appended; an export that pages through results repeats the last page; a failed upload is retried after part of it had already arrived.
  • Double submissions. A customer clicks “Pay” twice or refreshes a slow checkout page, or an app retries a request after a timeout.
  • System syncs. Two systems exchange records and one creates a new record instead of updating the existing one. The channel manager that passes bookings from travel websites to Harborview Hotel re-sends the whole booking each time it changes, and when a sync goes wrong it can create the same stay twice under two different booking references. The second kind is harder to catch, because the key itself differs: you have to compare the dates, room, guests and rate instead.
  • Joins. Combining two tables on a key that is not unique on one side repeats rows. If one customer appears twice in the customer table, joining orders to customers gives each of that customer’s orders two rows.
  • People. Two staff members register the same walk-in customer; an applicant applies to Northfield University twice with different email addresses.

The mechanism matters because it tells you which copy is right. A double click produces copies of one original. A sync produces a sequence of versions, of which the latest is usually the truth. A join produces copies that should never have existed, and the fix belongs in the join, not in the result.

What counts as “the same”?

Before you remove anything, decide what “the same record” means for this dataset. The business key is the column, or set of columns, that identifies one real-world thing in the business’s own terms: the order number for an order, the booking reference for a hotel stay, the student number for a student. In a well-designed database the business key is enforced as the table’s primary key, and the system refuses a second row with the same value. Exports, spreadsheets and merged files rarely enforce anything, which is how duplicates get in.

Sometimes no single column will do: a daily sales summary is identified by store and date together, a composite key. And sometimes there is no reliable key at all. A café’s till export that lists only date, product and price will contain two identical rows whenever two people buy a flat white on the same day. Those rows are identical, but they are not duplicates. Identical values are evidence that two rows describe one thing; they are proof only when the columns include something that should be unique.

The hard cases are repeats that could be genuine. A customer really can order the same bag of beans twice on the same day. To decide, look for evidence outside the columns you were comparing.

Key idea: Defined by the business, not by the data

Two rows are duplicates when they describe the same real-world event or entity. Identical values don’t prove it (two identical flat whites are two sales), and different values don’t disprove it (two versions of one booking are still one booking). Decide what one thing is, find its key, then look at the evidence.

The whole process of finding records that describe the same thing and reducing each group to one record is deduplication. It is a sequence of decisions, not a button: define the key, find the groups that share it, decide for each kind of group which record survives, leave the raw data untouched, and write down what you removed and why.

In depth

Exact duplicates, duplicate keys and how to count them

Call the number of rows nnn. Two rows are exact duplicates if they agree on every column, and key duplicates if they agree on the business key. Every exact duplicate is also a key duplicate, provided the key columns are part of the row, but not the other way round: rows 3 and 4 in the first table share a key but differ in the total. A key is unique when the number of distinct key values equals the number of rows. That is the uniqueness check you met when profiling data.

The number of surplus rows, the rows you would remove if you kept one per group, is the number of rows minus the number of distinct values (formula below). Count it twice: once on whole rows and once on the business key. If the second count is larger, the difference is the number of conflicting versions: rows that share a key with another row without being a copy of it. Those need a decision rather than a deletion.

Profile the key before you delete anything, because the pattern of repeats tells you how they arose. Count the rows per key value. Mostly ones with a scattering of twos suggests double clicks. A contiguous block of keys that each appear exactly twice suggests a file, or part of one, loaded twice. Keys that appear four or five times, with a different timestamp each time, suggest a sync that sends every change.

Choosing the survivor

When several rows share a key, a survivorship rule decides which one stays, or how they are combined. The rule should follow from how the duplicates arose, not from habit.

Four survivorship rules
RuleKeepsUse whenWatch out for
FirstThe earliest recordLater rows are re-sends of an original, as with double clicksFile order is not time order; sort by a timestamp first
Latest updateThe most recently updated recordLater rows are corrections or status changes: a modified or cancelled bookingNeeds a trustworthy updated-at or received-at column
Most completeThe record with the fewest missing fieldsCopies hold different amounts of detailA full record can be out of date: completeness is not correctness
MergeOne record built field by fieldEach source is best for different fieldsNeeds a rule for every field, and more review

Caution: “First” and “last” need an order

Keeping the first or the last row means first or last in some order, and the order of rows in a file is often accidental: exports may be sorted by customer, by the moment a server processed a batch, or not at all. Sort by a column that means something (created-at, updated-at, received-at) before applying either rule. Database documentation makes the same point: PostgreSQL’s DISTINCT ON keeps the “first” row of each group, which is unpredictable unless an ORDER BY fixes the order.

Merging is common for people and organisations, where each system knows something different. Lantern’s shop holds a verified email address, while the loyalty app in its cafés holds a phone number and a more recent postal address. A merged record (data teams often call it a golden record) takes each field from the source that is best for it and keeps a note of where each value came from.

How duplicates distort the numbers

A sum is inflated by exactly the values in the surplus rows, and a count by the number of surplus rows. Averages are subtler. Suppose there are nnn genuine orders with mean xˉ\bar{x}xˉ, plus kkk surplus rows whose mean is dˉ\bar{d}dˉ. The export reports

xˉreported=n xˉ+k dˉn+k\bar{x}_{\text{reported}} = \frac{n\,\bar{x} + k\,\bar{d}}{n + k}xˉreported​=n+knxˉ+kdˉ​

which equals the true mean only when the duplicated rows are typical, dˉ=xˉ\bar{d} = \bar{x}dˉ=xˉ. Duplicates are rarely a random sample. If a checkout page tends to time out on large baskets, the orders that get submitted twice are the large ones, and the average order value is pushed up as well as the total. Near duplicates distort different numbers: one customer under two email addresses counts as two customers, which inflates the customer count and the number of “new” customers, and deflates orders per customer.

Near duplicates and fuzzy matching

Many near duplicates disappear once values are standardised: trim spaces, put text in one case, remove punctuation, compare email addresses in lower case. The next two lessons cover these steps. After standardising, compare the values exactly again. What remains are differences of spelling, which need fuzzy matching: comparing values by how similar they are rather than whether they are equal, to find pairs that are probably the same.

The most common similarity measure for short text is edit distance, also called Levenshtein distance after Vladimir Levenshtein, whose 1965 paper “Binary codes capable of correcting deletions, insertions, and reversals” introduced it. It is the smallest number of single-character insertions, deletions and substitutions that turn one string into the other. “Nrth” is one insertion away from “North”. “Okafor” and “Okafro” are two edits apart, because swapping two neighbouring letters takes two single-character edits; some variants of the measure count a swap of adjacent letters as one edit.

Edit distance is computed with a table. Write one string down the side and the other across the top, each preceded by an empty position. The cell in row iii and column jjj holds the distance between the first iii letters of the first string and the first jjj letters of the second. The first row and column count up from zero, because turning jjj letters into nothing takes jjj deletions. Every other cell is the smallest of three moves: the cell above plus one (a deletion), the cell to the left plus one (an insertion), or the cell diagonally above-left plus nothing if the two letters match and one if they don’t (a substitution). The answer is in the bottom-right cell. Filling the table this way is usually credited to Wagner and Fischer (1974); the challenging example below works through one.

Raw distances favour long strings: one edit in a three-letter name is a big change, one edit in a twenty-letter product name a small one. A common fix is to turn the distance into a similarity between 0 and 1 by dividing by the length of the longer string (formula below). Even then, a cut-off on a single field makes errors in both directions. Set it loose and “Jon Lee” merges with “Jan Lee”, two different people; set it tight and “Jhon Reyes” stays separate from “John Reyes”. Practical matching therefore compares several fields at once (name, email, postcode, phone), and sends the uncertain pairs to a person.

Comparing every record with every other is also expensive: a list of 10,000 customers contains 10,000×9,999÷2=49,995,00010{,}000 \times 9{,}999 \div 2 = 49{,}995{,}00010,000×9,999÷2=49,995,000 pairs. Matching software therefore compares only pairs that share something cheap to check, such as the same postcode or the same first letter of the surname. This is called blocking, and its cost is that a pair split across two blocks is never compared.

These ideas come from record linkage, the statistical field that studies matching records within and across files. Fellegi and Sunter (1969) set out its classic framework: compare each pair of records field by field, use the pattern of agreements to judge how likely the pair is to be a match, and classify it as a link, a non-link or a possible link for clerical review, with the cut-offs chosen to control both kinds of error.

Finding duplicates in a spreadsheet, SQL and pandas

Spreadsheet. Sort by the business key, then add a helper column such as =COUNTIF(A:A, A2), which counts how many rows share this row’s key, and filter for values above 1 to review every repeated key. Excel’s Remove Duplicates command (Data tab, Data Tools group) deletes the duplicates permanently, and Microsoft notes that it compares the value displayed in each cell, not the value stored: the same date shown in two formats counts as two different values. Copy the data to another sheet first.

SQL. SELECT DISTINCT * FROM orders returns each distinct row once, which removes exact copies from the result. To list repeated keys, group by the key and keep the groups with more than one row: SELECT order_id, COUNT(*) FROM orders GROUP BY order_id HAVING COUNT(*) > 1. In PostgreSQL, SELECT DISTINCT ON (booking_id) * FROM bookings ORDER BY booking_id, received_at DESC keeps the latest version of each booking.

pandas. df.duplicated() marks each row that repeats an earlier one; df.duplicated(subset=['order_id'], keep=False) marks every row of a repeated key, including the first, which is what you want for review. df.sort_values('received_at').drop_duplicates(subset=['booking_id'], keep='last') keeps the latest version of each booking. The keep argument accepts 'first', 'last' or False (drop or mark them all).

Note: Never deduplicate the only copy

Leave the raw export untouched and write the deduplicated table to a new file or table, so the step can be rerun and checked. Record how many rows each rule removed and why; the last lesson of this course shows how to keep that record as part of a data quality report.

Common mistakes

  • “Identical rows are always duplicates.”

    Only if the columns include something that should be unique. A till export without transaction numbers produces identical rows every time the same item sells twice on a day, and deleting them deletes real sales. Before removing identical rows, ask whether two different real events could have produced them.

  • “If the rows aren’t identical, they aren’t duplicates.”

    Two versions of one order, or one customer under two spellings, are duplicates however different they look. Removing exact copies is only the first step: also count rows per business key, and look for near duplicates after standardising text.

  • “Same customer, same product, same day means a double order.”

    People reorder, buy gifts and split purchases. Look for evidence outside the compared columns: how far apart the orders were placed, whether there were two payments, whether two parcels shipped, and whether one order was voided.

  • “Keep the first row” is a safe default.

    The first row in a file is first only in the order the file happens to have. When later rows are corrections or cancellations, keeping the first keeps the outdated version, as the Harborview example showed. Choose the rule from the mechanism, and sort by a meaningful timestamp before keeping first or last.

  • “A small edit distance means the same person.”

    Short strings make distances misleading: “Jon” and “Jan” are one edit apart and are different people, while a transposed “Jhon” is two edits from “John”. Use several fields together, and review uncertain pairs.

  • “Remove the duplicates from the raw file and move on.”

    Deduplication involves judgement, and judgements get revisited. Keep the raw data unchanged, write the cleaned table separately, and record which rows each rule removed so that someone else can rerun or challenge the step.

In practice

Reconciling revenue. At month end Lantern’s bookkeeper compares the total of the order export with the payouts from the payment provider. A gap between the two is a prompt to profile order_id before anything else. She removes exact copies, resolves conflicting versions by keeping the latest update, and only then investigates what remains: refunds, fees and timing differences. If she skipped the deduplication, she would spend the afternoon chasing a “missing” payment that was never owed.

Counting customers. Ana wants to know how many new customers the shop gained in March and how many of them ordered again. Near duplicates bias both answers in the same direction: a returning customer who checks out with a new email address is counted as new, and the repeat-purchase rate falls because her history is split across two records. Matching customers on standardised email, name and postcode before counting changes the story Ana tells her bank about customer loyalty.

Running a hotel. Harborview’s revenue manager uses booked room-nights to set prices and staffing for the weeks ahead. Duplicate bookings from the channel-manager sync make the hotel look fuller than it is, which pushes prices up and hides the need for promotion. Her team writes the survivorship rule into the data pipeline (latest message per booking reference wins, cancellations included) and checks every week that booking ids are unique after the rule runs.

Student records. At Northfield University a student who changes programme can appear twice in a term’s enrolment extract, once under each programme. Whether that is a duplicate depends on the question. For a headcount of students it is: the unit is a student, so the business key is the student number. For a count of programme enrolments it may not be, because the unit is a student in a programme, a composite key. The same rows can be duplicates for one analysis and legitimate for another, which is why the key must be chosen before any rows are removed.

Across all four settings the professional habit is the same: say what one record represents, profile the key, decide the survivorship rule from how the duplicates arose, and measure the effect on the totals that matter. A deduplication that changes revenue by 0.1% needs a sentence in the report; one that changes it by 10% needs an explanation to whoever relied on the old figure.

Summary

  • A duplicate record describes the same real-world thing as another row. Exact copies, repeated keys with conflicting values and near duplicates need different treatment.
  • The business key defines “the same”. Identical rows are not duplicates when nothing in them should be unique, and different-looking rows can be versions of one record.
  • Separate double submissions from genuine repeats with outside evidence: timing, payments, deliveries and status.
  • Choose the survivorship rule (first, latest update, most complete or merge) from how the duplicates arose, and sort by a meaningful timestamp before keeping first or last.
  • Duplicates inflate sums by the value of the surplus rows and counts by their number; averages are biased when the duplicated records are not typical.
  • Edit distance counts the single-character insertions, deletions and substitutions between two strings; fuzzy matching should combine several fields and send uncertain pairs for review.
  • Profile keys with COUNTIF, GROUP BY … HAVING COUNT(*) > 1 or duplicated(keep=False); keep the raw data and record what you removed.

Terms introduced

Duplicate record
A row that describes the same real-world entity or event as another row in the same dataset.
Exact duplicate
A row whose values are identical to another row’s in every column.
Near duplicate
A record that describes the same entity as another but whose values differ slightly, for example in case, spacing, spelling or a second email address.
Business key
The column or columns that identify one real-world thing in the business’s own terms, such as an order number or booking reference.
Deduplication
Finding records that describe the same thing and reducing each group to a single record, or merging them, according to stated rules.
Survivorship rule
The rule that decides which record in a group of duplicates is kept, or how their fields are combined: for example first, latest update, most complete or merge.
Fuzzy matching
Comparing values by how similar they are rather than whether they are exactly equal, to find records that probably refer to the same thing.
Edit distance
The smallest number of single-character insertions, deletions and substitutions needed to turn one string into another; also called Levenshtein distance.
