Profiling a dataset and writing validation rules

Find out what a dataset really contains before you change it: profile every column, name each problem by the quality dimension it affects, and turn what you find into precise validation rules and a cleaning plan.

About 75 minutes

Before you start

You will be able to

  • Profile a dataset: its shape, types, blanks, distinct values, ranges, summary statistics and frequency tables, with cross-checks between columns.
  • Classify a data problem by the quality dimension it affects: completeness, validity, accuracy, consistency, uniqueness or timeliness.
  • Write validation rules of each kind (type, range, set membership, format, uniqueness, completeness, cross-field and referential integrity) and give each a severity.
  • Calculate completeness, a rule’s failure rate and the share of rows that fail at least one rule.
  • Explain why a value can pass every validation rule and still be wrong.
  • Plan cleaning from a profile by turning its findings into a prioritised issue list before changing any data.

Review first

  • Datasets: rows, columns, records and variables — You need the unit of observation, levels of measurement, primary keys and the data dictionary, which is what a profile is compared against.

What profiling is

Data profiling is the systematic description of what a dataset actually contains: for each column, the type of its values, how many are missing, how many are distinct, what range they cover and how they are distributed; and across columns, whether values that should agree do. Abedjan, Golab and Naumann (2015) describe profiling as determining the metadata of a dataset, and divide it into three kinds of task: profiling single columns, profiling combinations of columns, and discovering dependencies such as keys. The aim is not the statistics themselves. It is to find out what the data is before you decide what to do with it.

A profiling checklist

  1. Shape. Count rows and columns, and compare the row count with what you expected. If the shop’s dashboard shows fewer orders for the period than the file has rows, something has been repeated or extra rows have crept in.
  2. Types. For each column, compare the type the software inferred with the type the data dictionary expects. A price column read as text usually means some values contain characters other than digits.
  3. Blanks. Count empty values per column, and look for disguised ones: placeholder values such as 0, 9999, “n/a” or “unknown”.
  4. Distinct values. A primary key should have as many distinct values as there are rows; a column with a fixed list of categories should have no more distinct values than the list.
  5. Ranges. Find the minimum and maximum of every numeric and date column, and compare them with what is possible.
  6. Summary statistics. For numeric columns, the mean, the median, the quartiles and the standard deviation. A large gap between mean and median signals extreme values or a lopsided distribution.
  7. Frequency tables. For categorical columns, count each value. Spelling variants, unexpected categories and rare codes show up at once.
  8. Cross-checks. Test relationships between columns that must hold, such as a total that should equal its parts or an end date that should follow a start date.
  9. Extremes. Sort each important column both ways and read the first and last rows. Errors collect at the ends of a sorted column.

The summary statistics already change the answer to Ana’s question. The mean quantity is 54÷10=5.454 \div 10 = 5.454÷10=5.4 packs, yet the median is 1.5: half the rows show one pack or fewer. The single value of 40 supplies 40 of the 54 packs, and the sample standard deviation (dividing by n−1n - 1n−1) is about 12.2 packs, larger than every value except that one. Reporting 5.4 to the roaster without checking that order could mean roasting far more coffee than customers want.

Six dimensions of data quality

Profiling shows where the data departs from what it should be. To describe the departures consistently, practitioners use data quality dimensions: aspects of quality that can be assessed and measured separately. A widely used set of six comes from a 2013 white paper by DAMA UK, the UK chapter of the Data Management Association, and the UK government’s Data Quality Framework adopts the same six.

Completeness
The proportion of values present out of those that should be present. Lantern’s rating is optional, so blank ratings are not a completeness defect; a blank email, which is required, would be.
Validity
Whether values conform to their definition: the right type, format and range, and a member of the allowed set. A quantity of −1, a rating of 9 and the price “22,00” are invalid.
Accuracy
Whether values correctly describe the real-world thing or event. A quantity of 40 is valid, but if the customer ordered 4 it is inaccurate.
Consistency
Whether the same thing is represented the same way wherever it appears, within a table and across tables. North, north and Nth for one region are inconsistent; so are two rows that give order 5007 different quantities.
Uniqueness
Whether each real-world thing is recorded only once. Order 5007 appears twice.
Timeliness
Whether the data represents reality at the time it is needed and is up to date. An export taken before the day’s orders finished arriving is incomplete for that day; a booking marked “confirmed” after the guest cancelled is out of date.

Key idea: Validity is not accuracy

A value can pass every rule and still be wrong. Order 5009’s date, 6 May 2025, is a perfectly valid date; only its context (an export of May 2026, and an order number that follows orders placed in May 2026) makes it suspicious. Rules can prove that a value is impossible. Only a comparison with the real world, such as the payment record, the customer or the booking system, can prove that it is right.

In depth

Validation rules

A validation rule is a condition that a value, a row or a set of rows must satisfy, stated precisely enough for a computer to test. The European Statistical System’s handbook on data validation, published on Eurostat’s CROS portal, defines validation as checking whether a combination of values belongs to a set of acceptable combinations; each rule is a compact description of part of that set. Rules come from the data dictionary, from the business’s own logic and from the physical world: no stay lasts −2 nights.

Referential integritya value points to an existing row in another tableevery customer_id exists in the customer tableevery room_type exists in the room-type table

Four of these kinds have names you will meet often. A range check tests that a value lies between a minimum and a maximum. A format check tests that text follows a pattern; patterns are usually written as regular expressions, which lesson 5 introduces. A cross-field check tests a relationship between values in the same row. Referential integrity holds when every reference from one table to another points to a row that exists: an order for customer C77 is broken if the customer table has no C77. The referring column, here customer_id in the orders table, is called a foreign key.

Set membership and referential integrity shade into each other. A short, fixed list, such as three regions, can be written into the rule itself. A list that changes, such as the product catalogue or the customer list, belongs in its own table, and the rule becomes a check that every value exists there.

Hard rules and soft rules

Some rules must hold for logical or physical reasons. Eurostat’s guidance calls them hard (or fatal) edits, and a value that fails one is an error. Others flag values that are possible but suspicious; these are soft (or query) edits, and a failure means “check this”, not “this is wrong”. For Lantern, quantity of at least 1 is a hard rule: an order of −1 packs can’t exist as an order. Quantity of at most 20 is a soft rule: most customers buy one to three packs, so 40 deserves a look, but cafés do buy in bulk. At Harborview, check-out after check-in is hard; a nightly rate above the list price of the most expensive room is soft.

Give every rule a severity and an action. Hard failures are errors to correct or exclude, with the decision recorded; soft failures go to someone who can check them against the source. Neither kind is a reason to delete a row on sight.

Writing good rules

  • Testable. “Prices look sensible” is not a rule; “unit_price is a number greater than 0 and at most 100” is.
  • One condition per rule, with a name (R1, R2 …), so that a failure report says exactly what failed and where.
  • Explicit about blanks. Most rules quietly pass a missing value. In SQL a CHECK constraint is satisfied when its condition is unknown, which is what a comparison with a NULL gives, so CHECK (quantity >= 1) accepts a blank quantity. Pair each range or format rule with a completeness rule wherever the value is required.
  • Tolerant where arithmetic is. A cross-field rule on money should allow for rounding: the absolute difference between order_total and quantity × unit_price − discount is at most $0.01.
  • Sourced. Note where each rule comes from (the data dictionary, a manager, the laws of arithmetic) so that it can be challenged and updated when the business changes.

Measuring quality

Rules become measurements when you count their failures. A rule’s failure rate is the share of the rows it checks that fail it, and the share of rows failing at least one rule summarises a whole rule set. Report both. “R3 fails on 3 of 10 rows” tells the data owner where to look; a single score such as “the data is mostly clean” tells nobody what to fix. R7 is checked only on the seven rated orders, because blank ratings are allowed. The hard rules record nine failures but only seven rows fail at least one of them, because 5006 and 5008 each fail two.

Two features of that table matter whenever you measure quality. First, the denominator is the rows a rule checks, not all rows: R7 does not apply to blank ratings, which are a matter for completeness. Second, failures can’t simply be added: nine hard failures fall on seven rows, so 70% of the extract fails at least one hard rule, not 90%. Uniqueness can be measured the same way: 9 distinct order_ids among 10 rows is 90%.

Completeness needs the dictionary too. The rating column is 70% filled, but because rating is optional, its blanks are not a defect. A required column with the same 70% would be a serious problem: for email, it would mean three orders whose receipts couldn’t be sent.

Summary statistics need definitions too

Two statistics in a profile can differ between tools. The standard deviation can divide by nnn (the population formula) or by n−1n - 1n−1 (the sample formula). This course uses n−1n - 1n−1, as does pandas by default; NumPy’s std divides by nnn unless told otherwise. Quartiles have several definitions. The site’s tools interpolate linearly between sorted values, like Excel’s QUARTILE.INC and NumPy’s default, which gives a lower quartile of 1 and an upper quartile of 2.75 for the extract’s quantities. A rule that places the upper quartile at position 0.75(n+1)0.75(n + 1)0.75(n+1) in the sorted list gives 3.25 instead. Neither is wrong; say which you used.

Note: Six dimensions are a convention, not a law

DAMA UK presents its six dimensions as a checklist, not a complete list, and notes that not every dimension matters in every situation. Other frameworks divide quality differently: ISO/IEC 25012 (2008) defines fifteen characteristics, viewed from an inherent and a system-dependent perspective. The UK government’s framework describes quality as fitness for purpose: data good enough for one use can be inadequate for another.

From profile to plan

The output of profiling and validation is not a cleaner dataset. It is an issue list: each problem, the evidence for it, the dimension it affects and a proposed action, with the lesson of this course that handles it. Only when the list is complete do you start changing data, and then in an order that avoids creating new problems: fix types and formats before range checks (a price stored as text can’t be compared with 0), and resolve duplicates before counting anything.

Caution: Understand before you fix

Never change a value you haven’t profiled and explained. Keep the original export untouched, work on a copy and record every change. A “fix” made before the problem is understood, such as deleting every negative quantity, can throw away returns that the finance team needs, or hide a fault in the shop that will keep producing them.

Common mistakes

  • “Start cleaning with whatever looks wrong.”

    Fixing values before profiling the whole dataset means fixing symptoms one at a time, in an order that can create new errors, and sometimes “fixing” values that were right, such as a genuine bulk order. Profile every column first, write the issue list, then change data in a deliberate order.

  • “It passed validation, so it’s correct.”

    Rules test validity, not accuracy. A quantity of 3 when the customer ordered 2, a check-in date typed as the 12th instead of the 21st, a well-formed email belonging to someone else: all pass. Only a comparison with the source or the real world catches them.

  • “A range rule also catches missing values.”

    Most rules quietly pass blanks; an SQL CHECK constraint is satisfied when its condition is unknown, as it is for a NULL. Write a separate completeness rule for every required column.

  • “Rows that fail a rule should be deleted.”

    A failure is evidence, not a verdict. Soft rules flag values that may be genuine, and even hard failures often have a recoverable true value (swapped dates, a decimal comma). Deleting rows can also bias the result, as the lesson on missing values shows. Flag, investigate, decide and record.

  • “Blanks are the only missing values.”

    Placeholders such as 0, 9999, “n/a” and “unknown” fill a cell without supplying a value, so a column can look complete while hiding missing data. Count them during profiling. Conversely, a blank in an optional column, such as rating, is not a defect.

  • “Add up the failures to find the bad rows.”

    One row can fail several rules, so failure counts overstate the number of problem rows. In the extract, nine hard failures fall on seven rows. Count rows failing at least one rule separately.

In practice

Validation is most valuable when it runs automatically and early. Databases can enforce some rules at the moment data is written: PostgreSQL, for example, supports NOT NULL, UNIQUE and CHECK constraints (a CHECK can compare columns of the same row, such as CHECK (check_out > check_in)), primary keys and foreign keys, and it rejects any row that breaks them. Rules that need judgement, or data from several systems, are applied in the data pipeline each time a file arrives, with failing rows sent to a quarantine table for review instead of flowing into reports.

Harborview’s revenue manager (fictional) reports the average rate per room-night every Monday, and the channel-manager sync occasionally sends placeholder rates of 0 and 9,999. In a week with 300 room-nights sold at an average of $150, a single two-night booking carrying 9,999 raises the reported average to (300×150+2×9,999)÷302≈215(300 \times 150 + 2 \times 9{,}999) \div 302 \approx 215(300×150+2×9,999)÷302≈215 dollars, an overstatement of 43% that could prompt a price rise nobody intended. Two rules prevent it: rate above 0 as a hard rule (unless the booking is marked complimentary, which the data dictionary should say) and rate no higher than the most expensive room’s list price as a soft rule. The report runs only on rows that pass, with the failures listed beneath it.

Rules also work as an early-warning system when you track their failure rates over time. An online clothing brand (fictional) checks every day’s returns against the rule that a refund is no more than the price paid. For months the rule fails on a handful of returns a week; then, one Monday, it fails on a large share of them. Nothing is wrong with the returns: the brand’s new app has started including the delivery charge in the refund. That change of meaning would have silently inflated the returns figures if nobody had been watching the rule.

In each case the rules are cheap to write and to run. What makes them valuable is the discipline around them: a severity for every rule, a person who owns each failure, and a record of every decision taken because of one.

Summary

  • Profile before you change anything: shape, types, blanks, distinct counts, ranges, summary statistics, frequency tables, cross-checks and the extremes of each sorted column.
  • A profile shows where to look, not what is true: a suspicious value may be an error or a genuine event.
  • Six commonly used quality dimensions (DAMA UK, 2013): completeness, validity, accuracy, consistency, uniqueness and timeliness. Other frameworks divide quality differently.
  • Validity is not accuracy: rules can prove a value impossible; only the real world can prove it right.
  • Validation rules test type, range, set membership, format, uniqueness, completeness, cross-field relationships and referential integrity. Make each one testable, named and explicit about blanks, and give it a severity: hard for errors, soft for values to check.
  • Completeness = values present ÷ values required. A rule’s failure rate = failing rows ÷ rows checked. One row can fail several rules, so failure counts don’t add up to problem rows.
  • The output is an issue list and a plan, prioritised by the decision the data must support. Keep the original data unchanged and record every decision.

Terms introduced

Data profiling
Systematically describing what a dataset contains (types, blanks, distinct values, ranges, distributions and relationships between columns) before using or changing it.
Data quality dimension
One aspect of data quality that can be assessed and measured on its own, such as completeness or validity.
Completeness
The proportion of values present out of those that should be present.
Validity
Whether values conform to their definition: the right type, format and range, and a member of the allowed set.
Accuracy
Whether values correctly describe the real-world thing or event they represent.
Consistency
Whether the same thing is represented the same way wherever it appears, within a dataset and across datasets.
Uniqueness
Whether each real-world thing is recorded only once.
Timeliness
Whether data represents reality at the point in time it is needed and is up to date.
Validation rule
A precisely stated condition that a value, a row or a set of rows must satisfy, written so that a computer can test it.
Range check
A validation rule that a value lies between a minimum and a maximum.
Format check
A validation rule that a text value follows a pattern, such as an email address containing exactly one @.
Referential integrity
The condition that every reference from one table to another (a foreign key) points to a row that exists.
Cross-field check
A validation rule that tests a relationship between values in the same row, such as check-out falling after check-in.
